# AGENTS.md

- Employee contract signing links reuse the manager-only Kandidaten signing flow via an explicit query parameter; stop completion if signature storage, PDF upload or contract update fails. Why: mobile and desktop must produce the same signed document and never report success without persistence.

- Enforce mutually exclusive Verlet/work bookings per employee/day in database triggers on bookings and purchase-order lines; ignore rejected bookings and serialize on the employee profile. Why: all booking/approval/order paths must reject overlaps, including concurrent requests.
- Planning hour controls share net-duration conversion with a fixed pause; daily booking caps sum published planning only and exclude rejected bookings, serialized with planning writes on employee profiles. Existing over-limit bookings may be retained or reduced but not increased; unplanned days retain existing behavior. Why: drafts must not change booking capacity and client/approval/offline paths cannot bypass limits.
- Published planning booking eligibility depends on the day, never project_planning_status; future hour bookings are rejected by a database trigger using the Amsterdam business date. Why: live assignments must remain bookable today/past regardless of stale project status, including cached/offline views, without allowing future bookings.

- Never put real sales prices (tarieven) in client code, fixtures or `public/` assets; load them only from manager-only `spec_code_tarieven` via `loadSpecCodes`, which throws instead of falling back. Why: the JS bundle and public files are readable by anyone.
- The prijzenblad Excel template in `public/templates` stays price-free; prices are filled in client-side only after an authorised fetch, and the export aborts when that fetch fails. Why: the template is publicly downloadable.
- `projects` uses column-level grants: `authenticated` may only SELECT the whitelist in `PROJECT_SAFE_COLUMNS`; managers read sensitive columns via the `get_projects_admin_v1()` RPC (`adminProjects()`); the (week)planning reads only the columns it needs via `get_projects_planning_v1()` (`planningProjects()`), allowed for manager/uitvoerder/wv. Why: RLS cannot hide columns, so monteurs would otherwise see client/contact/sync data, and uitvoerder/wv may plan but may not use the manager-only RPC.
- Planner sync RPCs (`*_planner_planning_*_v1` write functions) are executable by `service_role` only; Edge Functions do the manager check first. Why: prevents direct calls with a user JWT.
- Desktop `/manager-planning` (lg+) writes to `planning_concept`; only the `publiceer_planning` RPC moves concepts into `planning` and it skips Planner-protected rows. Why: monteurs and hour booking read `planning` only, so drafts stay invisible until published.
- Desktop quick planning uses relative clipboard coordinates and bounded concept snapshots for undo; repeat scheduling loads live rows, concepts and availability across its full range before creating drafts. Why: cross-week actions must preserve day-specific fields and skip occupied or unavailable days without touching published planning.
- Desktop weekplanning row coordinates use the flattened rendered groups for selection, clipboard, drag targets and keyboard navigation. Why: positional actions must follow visible employees, not the pre-group sorting.
- The legacy project matrix (`ProjectPlanning`) never writes to or deletes from `planning`; only the weekplanning concept flow publishes. Why: the matrix used to wipe all project planning on (re)publish.
- `projects.soort` ('project' | 'uitleen') marks lending projects; uitleen reuses `adres` as default work location and `contactpersoon_naam/tel` as default contact, and skips phase, checklist, forecast and intake. Why: avoids duplicate columns and keeps klus logic unchanged.
- Desktop `/medewerkers` (lg+) uses `src/components/medewerkers/desktop/*`; certificate types keep their legacy DB names and are mapped for display only. Why: the mobile certificate flow depends on the existing names.
- `get_projects_planning_v1` has a fixed return shape; extra planning columns readable by `authenticated` (e.g. `benodigd_per_dag`) are fetched from `projects` separately and merged. Why: changing the RPC return type requires dropping it.
- Sales and cost rates live only in `verkooptarieven` / `kostentarieven` (manager-only RLS, rows with `geldig_vanaf`, never updated in place); resolve them only via `verkooptarief()` / `kostentarief()` (role row first, then `rol is null`; owners cost 0). Why: history must survive rate changes and rates may never reach the client bundle or non-managers.
- The financial overview (`/financien`, manager-only via `zietFinancien`) resolves rates client-side only through `bepaalVerkooptarief` / `bepaalKostentarief` in `src/lib/financien.ts`, which mirror the `verkooptarief()` / `kostentarief()` database rules, and takes project revenue only from `forecastOmzet` in `src/lib/forecastCalculatie.ts` (the same function ForecastTab and the forecast PDF use). Why: one rate rule and one forecast calculation, so a second version can never drift.
